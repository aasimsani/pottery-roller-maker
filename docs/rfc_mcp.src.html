RFC-001 · Pottery tools · Draft · 2026-11-02

Each pottery app gets its own MCP server that drives the open browser tab, so Claude can tweak a design while you watch.

The bridge reuses every line of the apps' drawing, library and print code, and it costs one open tab and about 400 lines per app. If Chrome ever blocks the tab's local socket, Claude falls back to the Chrome browser tools that work today.

Goals

  • Claude reads the whole design, which is the settings, the layers, the print check and the sizes, in one call.
  • Claude changes settings and layers, adds library designs and local images, and the tab rebuilds as it does after a click.
  • Claude sees the previews as images, so it can judge a design the way you do.
  • Claude saves checkpoints and goes back to one, so an experiment never loses a good design.
  • Claude exports the STL, the 3MF plate and the flat PNG to a path you name.
  • All three apps speak one protocol, so a tool learned in one app works the same in the others.

Non-goals

  • Running the apps without a browser. The drawing code needs a real canvas.
  • Remote access. The server only listens on this Mac.
  • Slicing or sending prints to the P2S. The 3MF goes to Bambu Studio as it does now.

04 · Chosen solution

A small Node server per app forwards each tool call to that app's tab, which applies it through its own setters.

  • A wins because it renders with the app's own code, so what Claude sees is exactly what prints, and you watch every change happen.
  • B loses because the art and library code would need a native canvas, an SVG renderer and a second copy of the sources, and the copy would drift from the UI.
  • C stays as the fallback, because it already works. It loses as the main path because each tweak takes several clicks and screenshots, and a renamed button breaks it.
  • D loses because the tab only reads localStorage when it loads, so every change needs a reload and nothing checks the values.

Trade-offs and caveats

  • A tab has to be open. The status tool says so, and open_app fixes it in one call.
  • Each server knows one app, so Claude sees three tool sets, such as mcp__pottery-roller__update_settings.
  • The 3D canvas keeps its last frame for screenshots, which costs a little GPU memory on every app.
  • A mutation waits for the worker. The first roller build takes about 4 s, so a tool call can take that long.
  • Screenshots cost tokens. Each one is scaled to at most 1200 px, which comes to about 1,500 tokens.

05 · Build plan overview

Each repo gains a server and a bridge, and the pipelines stay as they are.

new codeunchanged

  1. A tab loads with ?mcp=7343 and a launch token in its URL.
  2. The bridge connects, and the server compares the token with the one open_app made.
  3. A wrong token, or an origin outside localhost and aasimsani.net, gets the socket closed.
  4. A second good tab replaces the first, so commands always reach exactly one tab.

Option B in full

A headless server would import the pipeline and run it in Node. Lines layers already work there, because src/core/lines.ts draws without a canvas. Every other layer goes through renderTile() and loadArt(), which need a canvas, image decoding and SVG rasterizing. That means adding @napi-rs/canvas and an SVG renderer, and keeping a Node copy of each source in step with the browser one. You'd also lose the live view, so Claude and you would look at two different copies of the design.

Cross-cutting

  • Security. The server binds to 127.0.0.1 only, checks the origin and a per-launch token, and runs with your user's rights.
  • Privacy. No design leaves the Mac, apart from the library searches the app already makes.
  • Cost. Nothing new is hosted. Screenshots cost tokens in the Claude session.
  • Observability. The server logs each tool call to stderr, which Claude Code shows in its MCP log.

Untouched. The pipelines, the workers, the print checks, the mesh code and the Cloudflare deploy config stay as they are.
